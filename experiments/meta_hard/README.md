# 固定 M0/M1 的室内约束算法改进对照

从 `5261b1f` 开始；任务、初始程序、评分与预算在模型调用前提交于 **8bd759a**。
完整预登记见 [PROTOCOL.md](PROTOCOL.md)。M0/M1、原 SceneSpec/SceneState、
原 Verifier、原 walk 搜索、推箱子任务与冻结生成器没有修改。没有新训练、VLM、
GPU 渲染基础设施改动或新隔离框架。

## 实际结果与回答

**本轮 M1 在有限预算下的终测提升更高，差异不再来自静态审计；但尚不足以确认
它稳定地更擅长发现新算法。** 优势主要集中在一条 M0 连续失败轨迹，已返回布局
的质量仍接近天花板，M1 实际输入更多，而且 K=3 有两次流中断干扰。

共 3 个初始程序 × 2 个冻结策略 × 2 次独立采样，每种策略 6 条轨迹。K=2 未
饱和，按预登记统一扩展到 K=3，共 **36 次真实 CLI / 上游模型调用**，没有重试。
所有 29 个完整返回的代码都通过静态审计；另外 7 次没有形成完整可评估提案。

| 预算 | M0 MetaImp（均值 ± 样本 SD） | M1 MetaImp | 配对 M1−M0 |
|---|---:|---:|---:|
| K=2 | 0.7986 ± 0.3939 | 0.9722 ± 0.0505 | +0.1736 ± 0.4086 |
| K=3 | 0.8125 ± 0.3986 | 0.9722 ± 0.0505 | +0.1597 ± 0.4137 |

每格 n=6，配对单位是初始程序/模型重复，不是单张场景。初始程序终测分别为
first_fit 0/24、wall_priority 0/24、local_relations 1/24；基线对双方共享。
选中版本终测合计：K=2 M0 117/144、M1 142/144；K=3 M0 119/144、M1 142/144。
这些合计重复使用相同任务，不能当作 144 个独立统计样本。

按初始程序看，first_fit 的 M0 两次提升为 1.0 和 0，M1 为 1.0 和 1.0；
wall_priority 的 M0 为 1.0/0.9583，M1 为 1.0/1.0。local_relations 在 K=3 反而
是 M0 均值 0.9583、M1 0.9167。完整逐程序均值/SD 见
[per-fixture.json](results/per-fixture.json)。

单个 first_fit 重复贡献了 +1.0 的配对差值，占 K=2 平均优势的约 96%。
去掉该对后，其余五对均差在 K=2 仅 +0.0083、K=3 为 −0.0083。这不是替换主结果，
而是影响诊断：[全部配对值与逐对剔除分析](results/pair-influence.json)。
两次采样/程序、单一任务族以及较大离散程度不支持普遍优越性的结论。

### 审计、算法与执行分开看

| 指标 | M0 K=2 | M1 K=2 | M0 K=3 | M1 K=3 |
|---|---:|---:|---:|---:|
| 完整代码 / 提案槽位 | 10/12 | 10/12 | 15/18 | 14/18 |
| 静态通过 / 完整代码 | 10/10 | 10/10 | 15/15 | 14/14 |
| 通过审计后候选的选择集成功率均值 | 0.7750 | 0.9083 | 0.7778 | 0.9345 |
| 返回可用 SceneState 的选择任务 | 94/120 | 110/120 | 143/180 | 158/168 |
| 在可用状态上的完整任务通过率 | 98.94% | 99.09% | 97.90% | 99.37% |

同一轨迹内候选不是独立样本；上述条件均值仅描述候选质量，不是新的独立显著性
检验。完整 SD、执行失败与最短路径不足计数见
[summary.json](results/summary.json)、[stages.json](results/stages.json)。

双方都将局部贪心算法换成了包含约束传播、回溯和路径检查的通用有限域搜索。
M1 的预算内实现稳定性在这批运行中较好；但可用输出几乎都已满分，大部分剩余
差异来自能否在时间/CPU 限制内产生有效代码或状态，未观察到 M1 特有、跨任务族
验证的新算法类别。**新任务没有完全消除天花板效应，不能把较高均值解释为元级
改进已经得到确证。** K=3 的 12 条轨迹有 9 条终测满分，选择集中的满分候选也
经常无法再区分；固定选择器在同分时保留较早代码，不会用最终测试反向挑版本。

### 失败与选择机制

- `first_fit_1_M0`：c3 输出达到 Token 上限而不完整；c15 通过静态审计，但选择集
  12 个任务均触及 CPU 限制；c27 调用超时，最终保留未改进基线。它驱动了大部分均值差。
- `first_fit_0_M1`：c13 dev 12/12、选择集 11/12，失败类型为 `path_too_short`。
  下一轮 dense 开发探测独立找到了路径不足，c25 将选择成绩升到 12/12；没有把
  选择集失败任务交给模型。两个版本最终测试都为 24/24，不能把这次选择集修复
  计成额外终测增益。
- `local_relations_1_M1`：c22 dev 1/12、选择 4/12，主要为执行超限；控制器保留
  较早的 c10。该轨迹终测 22/24，同程序 M0 为 24/24，构成反例。
- c28 的 M0 新候选选择集仅 1/12，较早版本 12/12，被外部控制器保留。这说明
  模型的新提案不保证单调改善，不能用修改理由代替独立评分。

M1 第二轮有四条轨迹选择 dense，M0 始终选择 random；第三轮 M1 的 dense 探测
在部分 common 全通过的父程序上找到了额外 dev 失败。它实际改变了实验选择与
反馈覆盖，但新候选有成功也有退步；没有通过机制消融确认优势来自哪一部分。

另有 c33/c34 两次 M1 K=3 请求在 HTTP 200 后发生 `IncompleteRead`，分别持续
87.12/35.91 秒，原因未定位。按预登记保留消耗的槽位，不追加请求，但**不把流
中断算作算法或静态失败**。K=2 不受影响。K=3 排除这两个受影响的配对后均差为
+0.2604 ± 0.4934（n=4），仍高度受同一 M0 失败轨迹支配；这是补充敏感性分析，
不替换六对主结果。见 [proposal-failures.json](results/proposal-failures.json) 与
[transport-sensitivity.json](results/transport-sensitivity.json)。

也未把上一轮创建 M1 的成本混入本轮。

整轮真实运行墙钟 **3,405.27 秒（56.75 分钟）**。表中是请求时间之和，两路可
重叠，流中断会提前结束请求，不能据此断言 M1 提案更快。完整 CLI、请求时间、
用量与缺失标记在 [costs.json](results/costs.json)。父程序 dev 与候选 dev/selection

[execution-costs.json](results/execution-costs.json)；RSS 不是单个候选独立峰值。

旧转发器只在完整响应事件中记录 usage，超时、流中断及不完整输出造成缺失。
真实提案全部结束后，仅改进成本日志，使其他响应中可用的 usage 也能被记录，
并补充单元测试；没有改请求预算、评分器，也没有给历史数据估填 Token。

## 任务与边界

生成器在给定姿态域中摆放家具，输出完整 SceneState。固定桌子/结构柱、入口和
目标格均不可移动；必须满足所有 near_wall / in_front_of / keep_clear、原可达性
规则、碰撞检查与固定目标最短通路下限。下限取构造见证路线长度减 8/2/0 步，
且至少比曼哈顿距离长四步。不是提交一条绕远轨迹，也不能更换容易目标。
为兼容冻结元策略，指标中的 `solvable` 表示本轮全部硬条件成功数，`valid` 仍表示
原 Verifier 有效数；前者不是旧推箱子任务的可解数，也不只是导航路径存在。

三种难度有 6/6/11 件可动家具，每件 8/12/16 个姿态；房间旋转、对象标签匿名、
姿态顺序打乱。dev / selection / test 的尺寸组合不相交，分别使用不同固定种子。
每个输入均有原 Verifier、原 walk 与 PyBullet 检查通过的私有见证，见证不进入
模型或元策略请求。任务生成器与评分程序留在外部可信控制器。
各划分使用不同尺寸与输入，但仍属于同一种有限域关系/通路布局问题；不宣称是
全新任务族的泛化。固定目标和较长路径不自动保证算法发现过程足够困难。

三个此前未用于 M1 修订的初始程序为 first_fit、wall_priority、local_relations，
覆盖贪心装填、遗漏同时成立的墙约束、局部关系处理但无全局修订与路径难度目标。
它们的 selection 初始成绩均为 0/12；这不是复用旧的可移动方块/目标放置缺陷。

每个程序 × 每种元策略做两次独立 CLI 模型采样，共 12 条优化轨迹。每轮读取六张
公共 dev 图，加由原策略选择的六张探测图；候选选择用独立 12 图，最终测试 24 图。
先比较 K=2；仅在所有轨迹选择成绩都达到 12/12 时停止，否则双方统一追加 K=3。
总模型配额至多 36 次，每次一个上游请求、8192 输出 Token、180 秒 CLI 时间。
原始与改进后的元策略程序不再修改。

候选只在既有 Apptainer/seccomp 中运行，每个任务新进程、256 MiB、5 秒 CPU、
7 秒响应期限，输出有界、无文件/网络/进程创建/GPU/凭据访问。静态规则及资源
预算对双方相同。两路可信模型提案可以并行；候选与元策略执行保持串行。

选择以全部硬任务成功数为首要目标，原 Verifier 有效数仅用于成功数相同的情况，
再相同则保留较早版本。下一轮代码父版本只由 dev 决定，不读取 selection。
所有提案结束后才测试已选版本，最终反馈不再进入任何元策略或模型调用。

## 如何读结果

MetaImp@K 是选中版本最终测试成功率减初始版本成功率。报告每策略六条轨迹的
均值与样本标准差、每初始程序两次采样的结果，以及六个配对差值。n=2/程序仍很小，
不能据此断言统计意义上的普遍优越性。

同时区分调用/输出失败、静态拒绝、通过静态审计后算法质量、受限执行失败和最终
选中版本能力。通过审计后的候选质量使用 selection 成绩，最终测试仅评价预先选中
版本。均值不把被拒代码当成已经评估的劣质算法，也不把诊断平均分当成功率。

Token 以服务端返回的 usage 为准。超时或不完整响应可能没有最终 usage；这些
调用消耗配额，成本标为未知，已知 Token 之和只是下界。HTTP 200 或 SSE 结束不
代表生成了完整代码；实际 CLI 退出状态和候选结果分别保留。相同预算上限也不
等于相同实际投入，M1 可能选择更多、更长的样例，需要单独看实际成本。

保存模型输出和全部场景状态以便重新评分。模型采样不保证重现同一源代码；程序
中的无排序集合也可能造成进程间不同的并列选择顺序。离散程度包含这类执行差异，
不能全归因于模型随机性。评分重放检查保存的具体状态，不宣称逐字节重现生成过程。
