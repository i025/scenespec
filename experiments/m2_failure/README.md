# M1 根据失败反馈产生 M2：程序修订成立，元能力提升未证实

基于本地 `526a309`，先以零新模型调用分析旧 dev 记录，提交协议/控制代码 `3d1478c`；一次原生 Codex 编辑产生 M2，通过自动资格检查后在 `8719686` 冻结，再生成全部新条件。完成一个新初始生成器上的 M0/M1/M2 三组 K=1，没有追加模型采样或修补 M2。

**M2 的实际诊断和研究决策程序发生了改变，但本轮未证明元级能力提升。** M0、M1 的生成器候选在验证集入选，并在新私有终测通过全部原有门槛；M2 未入选。M2 原始候选在终测有更低偏好误差、更高位置多样性及 24/24 硬成功，但可见性降幅超过冻结门槛，不能事后补选或称为完整多目标收益。

## 1. 不调用新模型的失败分析

[失败机制报告](FAILURE_ANALYSIS.md) 只使用此前公开的 dev 查询/状态，未执行候选或增加 Mesh 查询。四个候选仍有随机提案，位置多样性下降不等于 RNG 消失。平均提案多样性 .398/.478/.484/.391m，最终变为 .279/.361/.426/.292m；距离更新和最小单次 loss 的历史选优均可能参与输出收缩。固定同一自适应提案流改选最后一个查询有效布局，通常保留更多变异但误差回升。

这些重放不能分离因果贡献，未对未选状态补验最终物理/通行成功。最终触边率还低于原基线，不能仅凭 clamp 将退化解释为边界挤压。外部版本验收拒绝四候选并保留 Repair，没有制造或部署它们的原始分布损失。完整 [数值轨迹](analysis/trace_analysis.json) 和 [训练反馈](analysis/training_feedback.json) 均来自 dev。

M2 创建任务只收到数值反馈与术语定义，不附本报告的手工修复建议、先前候选代码、验证/终测成绩或参考解。

## 2. 谁修改了什么

外部控制器调用原始 M1 的 `choose/propose`，输入旧 dev 失败经验及 M1 自身源码，保留它实际输出的分析、所选示例和提案指令。固定 meta 合约授权编辑父代策略，说明父代旧指令中的“只改生成器”属于下游阶段。原生 Codex 在独立最小 Git 工作区修改这份 M1 克隆，返回 Git patch；没有人工修改生成的策略。

这是控制器发起、M1 提案机制参与的一次策略程序修订。M1 没有自行决定何时开启自修改，也不能修改控制器或模型权重。Coding Backend、预算、评价器和 M0/M1 源码保持不变。

[M2.py](M2.py) 的程序变化包括：

- `_objective_evidence` 提取基线/候选的相对缺口，区分元级拒绝与物理失败，跳过未获最终验收的查询重放。
- `_diagnose` 按运行、可靠性、可见性和多样性缺口组织研究优先级。
- `_choose` 将实际瓶颈映射到已有探测菜单；未开放新的查询或预算。
- `_features` 读取实际 `packet.spec.room`；`_select` 使用配对指标、相同条件的不同种子与缺口调整示例排序/选择。
- `layout` 据测量生成目标组织和提案指令，不只是追加一段固定多样性提醒。

原有 AST 审计和受限执行通过。四种公开 schema 合成场景各做 choose/propose 共 8 个包，验证输出上限和非文本决策变化。相对父代，1 个包的实验选择发生变化，其他包还有文本/顺序变化；不是把所有文本变化都算作决策变化。这些检查是程序资格，不是独立能力成绩。真实 diff、父代输出、JSONL、Git 版本、资格记录见 [creation](results/creation) 和 [parent](results/parent)。

## 3. 独立小规模对照

只用一个预先登记的**新 group-restart 初始生成器**：[initial.py](initial.py)。它按支撑组重采样，包括同时重采样两个 floor 物体，区别于旧 Repair 的单物体更新；不是切换一个布尔参数。源码在 M2 创建前登记，但不挂载给创建 M2 的 Coding Agent。

M2 冻结后，原始任务分布生成全新 dev 8、验证 8、终测 12 个条件，每条件两种共享算法种子。28 个参考场景全部合法。去除 scene_id 后比较几何，未复用旧配对实验条件。新基线 dev 为 16/16、偏好误差 .27028m、位置多样性 .60647m，通过预定可行性检查，未调整初始程序或重采样条件来过关。

共同适配向全部三组提供相同的完整初始 dev 池多目标统计、配对元数据和相同历史 dev 失败统计。根据冻结策略选出的 12 条反馈及其汇总允许不同：M0 random、M1 dense、M2 barriers。这是相对旧研究的**共同信息扩展**，跨轮差异不能只归因于 M2。实际传给后端的示例：M0 为 `[0,1,2]`，M1 为 `[0,1,2,3,4,5,6,7]`，M2 为 `[6,7,2,3,0,1,4,5]`。M2 的示例集合与 M1 相同，只改变顺序，不能声称探测变化带来了更好的示例覆盖。

每个编码任务同样使用 gpt-6.1-sol medium、CLI 0.163.0、原生工具、600 秒、最多 6 次请求、每请求最多 4096 输出 Token、累计请求 1MiB、每请求 196608 字节、总服务 Token 400000。沿用原保守预留和未知用量拒绝逻辑。每次场景生成严格 24 次 Mesh/像素查询，原 LayoutProcess CPU/内存/PID/墙钟/输出限制及独立 MeshWorld 均未改动。

原 `eligible` 完整保留：硬成功不下降、无运行错误、可见性损失不超过 .01、全配对及合法配对位置多样性各保留至少 90%、旋转至少 80%、合法配对数不下降、偏好误差改善至少 .01m。验证选择封闭后才运行终测，不根据终测补选。

原始 M2 在终测位置多样性为基线的 104.2%，不能说“终测仍因位置损失失败”。它在此处的失败是**可见性平均下降 .01276，超过 .01**；虽然所有硬可见性约束仍满足，也不能忽略这条额外的多目标保持规则。姿态与布局同时改变，尚不能将可见性损失单独归因于随机初始朝向。M2 在 dev 的位置保留约 71.7%，不同划分的波动也提示两个种子的有限多样性估计存在噪声。

## 6. 为什么修改了元策略仍没有通过验收

三组实际生成了不同算法。M0/M1 保留原来前 23 次查询，只在最后一次对 incumbent 做小范围距离精修，单个 floor 物体总位移分别限制为 .12m/.05m；M2 随机化初始朝向，并在重采样与反复关系投影之间交替，从上一轮重采样状态精修。

保存的 dev 轨迹验证：M0/M1 各 368/368 个前 23 步输出与基线完全相同，精修总位移上限实测为 .12/.05m。M2 的每步投影虽有上限，累计精修相对前一轮重采样的最大 floor 位移却达 **1.498m**。局部步长有限不等于总位移小，也不保证跨种子分布保持。平均提案/最终位置多样性分别为：基线 .634/.606，M0 .624/.560，M1 .625/.596，M2 .568/.435m。它仍使用同一单次 loss 的历史选优。

M2 的实际分析将旧经验中的旋转缺口列为首要多样性瓶颈，并提出区分提案与最终选优；最终代码确实改变了初始化和搜索路径，却未稳定满足位置和可见性保持。这是诊断程序变得更明确、但诊断到生成器实现的转换仍不充分的实例。新统计支持上述可能机制，未做单因素消融，不能确定单个修改的因果贡献。轨迹证据见 [dev_trace_diagnostics](results/pilot/dev_trace_diagnostics.json)。

没有把改 .90 门槛、事后换验证划分或继续生成 M2.1 当成改进。本轮到此停止。
