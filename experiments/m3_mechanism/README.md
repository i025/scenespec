# Elite/r1 有效改进的离线机制归因

基于 `f36b91e`。M3 的具体候选在验证中更温和、四个任务族的位置分布更稳定；这解释了它为什么被选中。**不能据此认定 M3 的原始算法总比 M2 好：M2/Elite/r1 原始候选在终测也通过联合门槛，而且终测偏好、位置多样性和可见性均优于 M3。** 本轮没有模型提案、候选执行、物理重评分、重选或 M4。

## 实际研发路径

两条轨迹共享同一初始源码、96 条开发反馈池、模型 gpt-6.1-sol/medium、24 次 Mesh/像素查询、工具和外部预算。两者各交付 8 个样本、两个完整四种子组，但实际内容不同。依据为原始 [M2 task](../m3_reliable/results/elite_centroid/M2/r1/task.json)、[M3 task](../m3_reliable/results/elite_centroid/M3/r1/task.json) 和各自 `policy/choose`、`policy/propose`、`policy/delivery.json`。本轮机器可复核的摘录见 [inputs.json](results/inputs.json)。

| 环节 | M2/Elite/r1 | M3/Elite/r1 | 可以确认的事实 |
|---|---|---|---|
| 当前事实 | 开发硬成功 96/96、偏好误差 .234977m、位置 RMS .389245m、朝向 9.561726°；没有当前候选比较 | 完全相同 | 当前数据没有给出相对初始算法的保持率，无法实测当前候选是否退化 |
| 历史经验 | 4 次旧尝试均未接受，平均位置保持 .738176、朝向保持 .542853 | 同一历史记录 | 这是历史风险，不是当前初始算法的保持率 |
| 诊断 | “Measured acceptance bottleneck: rotation”，位置 deficit=.1798、朝向=.3214 | preference / hypothesis；引用 `summary.current.baseline.preference_error_m`，相对改善和保持率未知 | M2 的两个 deficit 分别等于 (.9−.738176)/.9 和 (.8−.542853)/.8，来源是历史 |
| Probe | barriers，可用条件 4、5 | random，可用条件 2、3 | 选择机制改变了可见反馈池 |
| 真正交付 | 开发条件 5（doorway）和 0（inclined），各 4 个种子；偏好误差组均值 .053299、.005318m | 条件 2（occlusion）和 1（doorway），各 4 种子；.016819、.016195m | 两组都确实交付了完整 Probe 组；既不是只改示例顺序，也不能说 M3 展示了残差更大的样本 |
| 研究指令 | 优先朝向，包含保持多样性门槛，但仍带有旧棋盘/可逆构造术语与完整源码输出措辞 | 连续 u/v/yaw、四种子成对比较、有界局部修复；单布局 loss 不保证分布质量 | 最终原生编辑接口仍相同；文本差异不直接证明收益因果 |

M2 的历史遍历路径见 [M2.py](../m2_failure/M2.py#L58)：`_objective_evidence` 递归读取整个 summary，`_diagnose` 对风险取最大值；日志与历史数值一致。M3 的实际入口见 [M3.py](../evidence_m3/M3.py#L301)：`_current_diagnosis` 只从 `summary.current` 和当前示例建立事实，`layout` 决定 Probe，再由 `_condition_groups` 交付完整条件组。两个 CLI 的成功读取事件见各自 [M2 events](../m3_reliable/results/elite_centroid/M2/r1/coding/attempt0/events.jsonl)、[M3 events](../m3_reliable/results/elite_centroid/M3/r1/coding/attempt0/events.jsonl)。没有执行未走到的旧函数来冒充实际路径证据。

M3 的当前诊断函数实际上不读取 history 来计算瓶颈；历史仍包含在相同输入包中。它没有从历史自动推导出6cm或query=16：这两个常数是本次 Coding Agent 自主写入的算法选择，不能称为元策略已经学会了最优步幅。

| 修改 | M2 | M3 |
|---|---|---|
| 搜索父代 | 从 top-3 中随机选单个父代，替代原精英均值 | 保留精英均值与原随机数消费路径 |
| 修正起点 | 从 query=8 起，后 16 个提案 | 从 query=16 起，后 8 个提案 |
| 关系修正 | 每个提案 8 轮，单步为一半距离残差，没有额外的每物体移动上限 | 每个提案一轮，每物体累计路径长度至多 .06m |
| 边界与中点 | 先等反向移动，再分别 clamp；发生不同裁剪时中点可能改变 | 两端使用同一裁剪比例，单次关系更新保留中点 |
| 其他保护 | 仅处理 floor-floor 关系，高度修正；无修正前后解析总误差回退 | 跳过带混合支撑关系的端点；修正后 floor 解析总偏好误差不下降则回退 |
| 朝向、最终筛选 | 初始 seed yaw 保留，最终仍取单布局 `optimizer_loss` 最小值 | 同样；没有添加跨种子分布评分器 |

## 可以归因到什么程度

1. **代码与真实路径证据：** 历史事实分离、Probe 内容和研究指令确实不同；M3 产生了晚启用、小步、对称裁剪的算法，M2 同时改变父代和更强关系投影。两者查询数相同，无额外拒绝采样；保留 yaw 与实际朝向100%保持一致。
2. **离线统计关联：** M3 的小幅修正与验证分布更稳定同时出现，M2 在部分验证族的提案已收缩；这支持“受限干预减少特定条件上的分布扰动”这一解释。M2 的终测更好，则表明算法适用条件和有限验证选择也是重要因素。
3. **未证明的因果作用：** 没有逐项移除 6cm 上限、晚启用、父代变更、公共裁剪或回退；也没有固定反馈/随机提案、只切换元机制的实验。一次配对不能把成功归给 M3 某个单独机制，更不能认定普遍元能力优势。

若未来专门做算法机制实验，应仅在**新的开发条件**上，对已冻结候选一次只切换一项机制并使用相同四种子/24查询，先报告交互未知；不要拿本轮终测调节 6cm 或启用时刻。本轮没有执行该干预，也不把历史消融结果移植成当前候选的因果证据。

## 未来容量错误处理与测试

只修改既有 [run_m3_reliable.py](../../scripts/run_m3_reliable.py)，原 `scene_rsi/meta/coding.py` 不变。新参数仅在未来 `--phase freeze --retry-stream-overload` 登记，execute 从 frozen.json 读取；默认关闭，历史规则和所有历史结果未改。

新增类别严格限制为：逻辑尝试中仅一个上游首请求、HTTP200、SSE 有 `response.failed` 且 code=`server_is_overloaded`、未知 usage、无模型输出/工具 item、无 Diff/源码变化。错误对象的 `headers` 是本次实际服务返回 Retry-After 的位置；不依赖 CLI 错误文案分类，不记录认证头。读取 Retry-After 秒数/HTTP日期和 retry-after-ms；同时存在时取较大值，等待 max(原30/60秒退避, 服务要求)。缺失或非法值不猜测等待时间，记容量失败。每次等待分为至多30秒的小段，但总等待不缩短。

最多两次重试，全部请求、未知 Token 预留、输入字节及墙钟累计。服务等待无法放进剩余600秒，配额耗尽或次数用尽，记 `service_capacity_failed`，不重新获取逻辑预算。普通代码/审计/算法失败不重试。已知 usage 与未知请求分开保存，未知不计零。仍只重试未产生代码的首请求容量错误，不恢复半成品。

原两条响应离线重放识别到327/320秒，按原实际已耗时计算，首次等待后分别剩267.72/275.50秒；**不知道重试能否完成**，尤其再遇同样长等待时无法放进预算。见 [service_replay.json](results/service_replay.json)。这是新规则的分类演示，没有补跑原槽位。

9项新容量回归使用假后端、虚拟时钟和原始 SSE，覆盖真实327/320、累计四项预算、第二次长等待、重试上限、未知usage、缺失/非法日期、已编辑/输出/后续请求/其他错误拒绝、默认历史行为。另3项分析回归和原7项调度回归共19项通过；完整 **296项通过，32.667秒**。最初受限权限下8项本地 socket 测试被系统拒绝绑定，保留失败日志；获准运行本地假服务后全量通过，没有研究推理请求。见 [checks](checks)。
