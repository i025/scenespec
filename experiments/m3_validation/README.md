# 冻结 M2/M3：重复配对与机制检查

**没有得到可部署的重复多目标改进，也没有证明 M3 普遍优于 M2。** 从 `2bb85f6` 开始，按预登记的两新初始程序、两次独立采样尝试全部 8 个正式槽位：5 个完成原生编辑、静态审计与隔离评价；3 个首请求被服务端以 HTTP 429 / `turn_rate_limit_exceeded` / `Codex is at capacity` 拒绝，没有补抽。M3 在第二初始程序的两个槽位均未产生代码，因此完整的跨初始程序公平比较未完成。

5 个可评价候选全部被选择集拒绝，双方最终版本均保留各自基线，原 MetaImp@1 和完整有效改进率均为 0。M3 的两个原始候选随后都通过新私有终测的联合门槛，这是同一初始程序上的有限重复信号；它不能替代事先固定的选择决定，也不能弥补另一个初始程序缺失的结果。不生成 M4，不修改策略或门槛。

## 冻结、数据和调用规则

正式调用前提交 [协议](PROTOCOL.md)、[新初始算法说明](INITIALS.md)、控制器和测试（`8d02402`），机制负控范围收窄于 `1e35f59`，实际开发机制与两个消融槽位于 `4891f7e` 固定。M2、M3、原生 Codex 后端、受限执行器、SceneSpec、MeshWorld、Verifier、资产及原 `eligible` 均未改动，见 [Git 内容比较](checks/frozen_scope.json)。

- `sequential_projection`：每种子固定朝向，随机连续位置，一轮有序关系投影及边界截断；没有联合回访。
- `shared_shift`：随机布局骨架，查询仅能共同平移或共同转向；不能独立改变物体间距离。

二者预先编写并冻结，不是过去 coordinate_walk / whole_restart 的复跑。复用原四个任务族，没有增加场景类型。每初始程序新建 dev 6、selection 6、私有 test 12 个条件，每条件 4 个共享随机种子；另有独立消融 dev 6 个条件。共 54 个合法参考场景先由可信 MeshWorld 验收；参考解、选择/终测条件和种子均未提供给 Meta/Coding Agent。没有按成绩重采样，接口预检不要求满分。

同初始程序的四轨迹使用完全相同的原始 24 条开发反馈与统计。两策略各自选择恰好 8 条反馈，完整保留两个条件的四种子；控制器没有补例、截断或重排。相同策略两次 Coding Task 在 JSON 边界完全一致，使用独立 CLI 会话和工作区，不共享前一候选结果。r0 按 M2→M3、r1 按 M3→M2 提交，固定并发 2，不根据结果调度。

## 元策略真正改变了什么

正式任务和 choose/propose 日志显示：两初始程序的当前输入均只有基线，没有当前候选比较。M2 仍写出“Measured acceptance bottleneck: rotation”，其 deficits 与历史位置/旋转保持率精确对应；M3 把当前偏好改善标为 `hypothesis`，比较退化仍未知，明确历史不能建立当前违反项。

| 初始 | 策略 | 实际 Probe | Coding Agent 实收条件，各四种子 |
|---|---|---|---|
| sequential | M2 | barriers，候选 4/5 | 4、1 |
| sequential | M3 | random，候选 2/3 | 2、0 |
| shared | M2 | barriers，候选 4/5 | 4、0 |
| shared | M3 | random，候选 2/3 | 2、0 |

这确实改变交付成员，不是仅重排文字。M3 的研究任务还要求连续坐标、有界修复、保留种子变化，并警示单场景 optimizer_loss 不是分布指标；M2 保留一些 board/deadlock/path 的通用旧任务用语。固定多目标门槛两方都收到。证据见每轨迹 `task.json` 与 `policy`。

5 个完成候选都是算法逻辑修改，初始化和最终 `best_index()` 未改：

- M2/sequential/r0：支撑旋转后的真实中心、三维距离转水平圆约束、圆与边界交点搜索。
- M2/sequential/r1：三维高度修正、多轮投影及边界截断/停滞终止。
- M3/sequential/r0：投影后双端有界修复、8cm 限制、回退线搜索、偏好下降及距离硬违规不增加检查。
- M3/sequential/r1：单端修复、累计 8cm 行程、坐标关系过滤、改善检查及回滚。
- M2/shared/r0：相对方向的独立物体位移，突破只共享平移的限制。

M3 两次把有界修复方向落成代码，可以确认程序行为的重复性；其性能表现只能与整套任务相关，不能把收益单独归因于诊断或 Probe。8cm 限制针对查询内修复，最终赢家查询可能改变；没有跨种子分布验收，不能把局部移动上限等同于最终多样性保证。

## 开发集单机制消融

全部变体是受限环境中的副本，冻结 M3 原文件未改；原验证器的拒绝原样保留。26 次离线策略执行均正常退出，模型调用 0，结果见 [offline_ablation](results/offline_ablation)。

| 单独移除机制 | 独立实测开发输入 | 清楚标记的合成反事实 | 可得结论 |
|---|---|---|---|
| 历史/当前分离 | preference/hypothesis、random、条件 1+3 → rotation/observed、barriers、条件 1+4 | 历史风险可污染当前事实 | 真正改变诊断及交付；负控因将历史标为 observed 被原校验器拒绝，不是合格替代策略 |
| Probe 优先交付 | 诊断、Probe、成员和提示均未变 | 交付条件 0+2 → 0+1，保留四种子和八例 | 路径可真正改变后端输入，但本次实际开发输入未激活差异 |
| 数字裕度 | 非文字决策不变，仅提示改变 | 80°→72°：移除 80% 容差后才触发 rotation/observed、barriers | 硬编码阈值比较有效，实际开发输入无行为差异证据 |

另将输入 `constraints` 改为旋转保持 95%、最低偏好改善 0.3m，M3 完整响应不变：它使用程序中的固定数字，没有动态消费该输入。外部合同与可信验收仍执行原门槛；这限制的是策略对新约束的适应性，不是评分器失效。文字变长、仅顺序/证据路径改变均不计作实质机制生效。
